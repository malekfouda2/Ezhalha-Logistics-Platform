Dangerous Goods on Mobile

Dangerous goods do not behave like an Express shipment. Carriage is arranged with the carrier by email, so nothing is priced when the client submits — no rates, no payment, no waybill. A price arrives later as a quotation, and the shipment is booked only after it is paid. The wizard therefore ends where Express is barely half done, and the rest of the flow happens in a different session, days later.

What is different from Express

You have already built Express. These are the only places dangerous goods diverges — read this table before anything else, because four of the six differences are things Express does that dangerous goods must not do.

Express doesDangerous goods does
Fetches rates, client picks a service No rate step at all. There is nothing to fetch — the price comes from a human conversation with the carrier
Pays at the end of the wizard No payment step. The wizard ends on a submission receipt showing Charged so far: nothing
Books the carrier on payment, returns a waybill and label Payment books nothing. An operator confirms with the carrier by hand afterwards
Calls /api/client/shipments/confirm after paying Never call confirm. The server short-circuits it for a paid DG shipment
Anyone with create_shipments can start it Gated per account — an admin must approve dangerous goods access first
One session, start to finish Two sessions. Submit now; come back through a notification to pay

The shipment's life

Six states, four of which are new to the app. Every one needs a badge in the shipment list and a sensible detail screen — a shipment sitting in dg_booking for a day with no explanation is a support call.

0 Gate

Access is per account, not per user

Check the gate before you show the tile. If the account is not approved, the tile stays visible but leads to a request screen — hiding it entirely leaves a client with no way to ask.

GET /api/client/dangerous-goods
{ "enabled": false, "request": { "status": "pending" } | null }
POST /api/client/dangerous-goods/request

Render three states from request.status: pending (“under review”, no button), rejected (show the reason, allow re-request), and null (show the request form).

Only the primary contact may request access — the endpoint is behind requirePrimaryContact. A sub-user gets 403. Check user.isPrimaryContact and explain rather than letting the request fail.

5 New

Content kind — the one thing only the client can answer

This choice decides which carrier service and content id the shipment can ever be booked under, so an operator cannot infer it afterwards. A single-select list, 14 options, one line of plain-language description each.

Sets two fields on the declaration:

dangerousGoods.contentKind : DgContentKind   // required
dangerousGoods.regulation  : "IATA" | "ADR"  // required, default IATA

The full list and its copy is in client/src/pages/client/create-shipment.tsx → DANGEROUS_GOODS_CONTENT_KINDS. Lift the labels verbatim; they were written for people who do not know IATA packing instructions by number.

6 New

Upload the sheet, let the server read it

Three calls, in order. The first two are the standard upload dance you already use for trade documents.

POST /api/uploads/request-url
PUT <uploadURL> — raw bytes, no auth header
POST /api/client/shipments/extract-dangerous-goods
// request
{ "fileName": ..., "objectPath": ..., "contentType": ... }

// response
{
  "commodities": [{ "unNumber": "UN1993", "hazardClass": "3",
                    "packingGroup": "II", "missingFields": ["quantity"] }],
  "productName": "ACME Industrial Cleaner 400",
  "notDangerousGoods": false,
  "warnings": ["Some transport details were not stated in this document."]
}

Extraction pre-fills; it never blocks. Show what came back, show the warnings, and let the client continue regardless — operations completes anything missing before a carrier sees it.

Handle three outcomes. Success with commodities; success with notDangerousGoods: true (tell them this may not need the DG flow at all, but let them proceed); and failure — the upload or the read can fail, and the client must still be able to go on. A silent failure here produces a declaration nobody checked.

9 Receipt

The wizard ends here

No rates, no card form, no label. Say plainly that nothing has been charged and that a quotation is coming — this screen is doing expectation management, and it is the last thing the client sees for possibly a day or two.

Clear the draft store on unmount, exactly as createShipment/express/_layout.tsx does. A stale dangerous goods draft surviving into the next shipment is worse than a stale Express one.

…then, a day or two later

Everything below happens in a fresh session, reached from a push notification. This half is the part most likely to be missed, and it is where the money is.

A Re-entry

The notification is the entry point

Operations sends this the moment a price is entered. It carries an actionUrl of /client/quotations/:shipmentId — map that to your quotation route in the deep-link handler.

type: quotation_created entityType: shipment entityId: shipmentId

The same shipment is also reachable from the shipment list, sitting at payment_pending. Both routes must land on the same screen.

The quotation has an expiry. Surface the date everywhere you surface the price — after it lapses the server refuses payment and operations has to re-confirm with the carrier.

The client is the offeror of the goods, so they re-confirm what operations left before any money moves. Show the completed declaration — not the one they submitted — because it may have changed.

shipped bug Do not offer Pay before this is done

On web, the shipment list offered “Pay Now” for a DG quotation while consentAccepted was still false. The card tokenised, the request went out, and the only answer was 400 — “Please confirm the dangerous goods declaration before paying.” with nowhere in that screen to confirm. A complete dead end. D Payment

Two ways to pay, one way to walk away

POST /api/client/shipments/pay
{ "shipmentId": "...", "tapTokenId": "...", "returnPath": "..." }
POST /api/client/shipments/:id/pay-later

Credit only — show it when creditEnabled and available credit covers the total.

POST /api/client/quotations/:id/decline
{ "reason": "optional free text" }

Declining cancels the quotation and charges nothing. Nothing is booked with the carrier at this point, so say so — “nothing to cancel” is reassuring and true.

important Never call /api/client/shipments/confirm

Express calls it after payment to trigger the carrier booking. For dangerous goods there is no booking to trigger — the server short-circuits the call and returns the shipment unchanged. Harmless, but it means your success handler must not wait on it, and must not treat its response as “booked”.

E New state

dg_booking — paid, not yet booked

This state has no equivalent in Express and it can last hours. The client has paid and is waiting on us; if the app shows a bare status string with no explanation, they will call support.

status: dg_booking paymentStatus: paid carrierTrackingNumber: null
Guard every waybill and label affordance on carrierTrackingNumber being non-null, not on paymentStatus === "paid". In this state the shipment is paid and has no waybill, no label and no tracking events. A “Track” button here leads to an empty screen.

Cancelling is still allowed here and is cheapest at this exact moment — nothing is booked, so it is a clean refund. Keep the cancel action available.

F Live

Booked — ordinary from here

Once operations records the air waybill the shipment becomes created and behaves like any other: carrier tracking syncs, the pickup is booked, milestones arrive as normal notifications. Reuse the Express detail screen wholesale.

Show both numbers, always. The Ezhalha reference (trackingNumber) and the carrier air waybill (carrierTrackingNumber) are different things. Collapsing them — showing the waybill in place of the reference once one exists — reads as the shipment being issued a new number partway through its life. That bug shipped on the ops hub and had to be fixed; do not repeat it here.

Traps

Every one of these is a real defect that reached staging or production during the web build. They are listed because they are cheap to avoid up front and expensive to find later.

1 No rate step, no payment step in the wizard

Do not copy Express steps 6–8. There is no rate to fetch and nothing to pay for yet. The flow ends on a receipt.

2 Payment lives in a different session

If you only build the wizard, the feature does not work. The quotation, consent and payment screens are half the job.

3 Consent gates payment everywhere

Shipment list, quotation screen, deep link. Any surface offering Pay must check consentAccepted first, or it is a dead end.

4 An expired quotation cannot be paid

The server returns 400 once dangerousGoods.expired is true. Check it client-side and show “Operations will re-confirm the price” instead of a Pay button.

5 dg_booking must render in the list

An unknown status usually falls through to a grey “—” badge. Four new statuses need labels, colours, and a place in the filter tabs.

6 Guard on the waybill, not on paid

Between payment and booking the shipment is paid with no waybill, no label and no tracking. Anything keyed on “paid means booked” breaks in that window.
